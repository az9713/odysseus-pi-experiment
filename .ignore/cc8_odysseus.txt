  ollama run gemma4:e4b does two things — starts the server and drops you into
  an interactive >>> chat prompt that occupies your terminal. You'd type /bye to  leave the chat (the server keeps running). The only part I actually need is     the server (the API on :11434); the interactive chat is irrelevant for the
  test. The one upside: it pre-warms the model, so the first test turn won't
  cold-start.

  What I actually need is just the server reachable at http://localhost:11434.
  Two cleaner options:

  - ollama serve in a terminal you leave open — starts only the API, no REPL.

  Why you (not me) should start it: when I started ollama serve as a background

  What was wrong (why it "took so long" = it was hung)

  The run wasn't slow, it was deadlocked. Diagnosis via a direct pi spawn
  surfaced the actual error:

  Error: Unknown provider "odysseus"

  My bridge extension registered the model provider via
  pi.registerProvider("odysseus", …), but pi resolves --provider at startup,
  before extension factories run in rpc mode — so the provider didn't exist yet,
  pi errored immediately, the model never loaded, and my backend sat forever
  waiting for events that never came (hence the empty session dirs and lingering
  process). (--list-models had shown it because that path loads extensions
  first — a misleading green light.)

  The fix (applied)

  Switched to the mechanism Phase 0 actually proved works: a per-session
  models.json that pi reads at startup via $PI_CODING_AGENT_DIR, with --provider
  selecting it. I verified this end-to-end before changing the real code — a
  bare rpc turn returned agent_start → "Hello" → agent_end cleanly.

  Concretely:
  - pi_backend.py now writes a per-session models.json + sets
  PI_CODING_AGENT_DIR, and selects --provider odysseuslocal.
  - The bridge extension is memory-only now (dropped registerProvider), and I
  added an 8s fetch timeout so a slow Odysseus can never hang a turn (the
  original failure mode would've recurred there otherwise).
