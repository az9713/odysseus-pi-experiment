  Verdict: Yes, they compose — but asymmetrically

  The framing everyone would assume is wrong. Odysseus's README says its agent
  is "built on opencode," but ACKNOWLEDGMENTS.md:22-26 reveals opencode's
  patterns were ported into native Python (src/agent_loop.py) — there's no
  embedded agent runtime to swap pi into. So the analysis splits into two
  directions:

  Direction A — pi as a client of Odysseus: nearly free, high value

  1. Odysseus's Claude Code integration transfers to pi almost verbatim.
  Odysseus ships its agent integration as an Agent Skill
  (integrations/claude/skills/odysseus/SKILL.md + API script) calling the
  scope-gated /api/codex/* REST API. Pi implements the same agentskills.io
  standard and explicitly documents loading ~/.claude/skills (skills.md:43-62).
  One settings line + two env vars → pi gets todos, email, calendar, memory,
  documents, Cookbook — all enforced server-side by Odysseus tokens.
  2. Pi runs on Cookbook-served models. Odysseus's vLLM/llama.cpp serves are
  OpenAI-compatible; pi consumes them via one models.json entry
  (models.md:18-35). One GPU, one model pool, two tools.

  Direction B — Odysseus embeds pi as a coding-agent backend: feasible, but
  gated

  Pi's RPC mode (JSONL over stdio, 27 commands, streamed deltas, with a Python
  client example in pi's own docs) maps cleanly onto Odysseus's existing SSE
  chat streaming and subprocess-management precedents. But one issue is marked ⚠
  UNRESOLVED: Odysseus enforces fail-closed per-user tool gating
  (src/tool_security.py:14 — verified first-hand), while pi by design has no
  permission system at all (what-is-pi.md:63). Embedded naively, every pi
  session gets full server-process shell access, bypassing every Odysseus gate.
  Mitigations exist (admin-only sessions, containers, a tool-intercepting pi
  extension) but all require engineering decisions no config can substitute for.

  Also marked: Node ≥22.19 dependency (⚠ friction), duplicated
  session/skill/model state (⚠ friction), skill-lifecycle one-way street (⚠
  unresolved), and MCP deliberately rejected by pi — the REST API is the right
  bridge, not MCP.

  ★ Insight ─────────────────────────────────────
  The deepest compatibility here isn't technical, it's philosophical convergence
  from opposite directions: pi rejected MCP in favor of "CLI tools + skills +
  bash" (design-rationale.md:15-19), and Odysseus independently built its
  external-agent surface as exactly that — a skill wrapping a scoped HTTP API.
  Two projects that never planned to interoperate ended up sharing an
  integration grammar, which is why Direction A costs ~nothing.
  ─────────────────────────────────────────────────

  Three open questions at the end of the report need your call — chiefly: is the
  goal pi-for-you-the-admin, or coding-agent-for-all-Odysseus-users? That
  answer decides whether Direction B is a weekend or a project.

  1. A long-horizon agent that actually knows you

  - Odysseus alone: has your life context (memory src/chat_processor.py:24-31,
  email, calendar, todos) but its loop can't run long — no compaction, max 50
  rounds (src/agent_tools.py:22), context just fills up.
  - pi alone: can run for hours — auto-compaction (rpc.md:354-393), session
  trees — but is amnesiac about you: no memory, no personal data, by deliberate
  design (what-is-pi.md:61-65).
  - Combined: "go through this 200-email backlog, update my todos and calendar,
  maintain a summary doc" becomes runnable. The task needs both durable personal
  context and a loop that survives 100+ turns. This is the headline gain.

  2. Context-preserving model escalation — Odysseus's best idea, properly
  realized

  - Odysseus's teacher/student escalation (src/teacher_escalation.py) re-runs a
  failed task on a stronger model — it restarts, losing the session's
  accumulated state.
  - pi's set_model switches models mid-session, keeping the full conversation
  (rpc.md:217-233; what-is-pi.md:13 — "hand it from Claude to GPT-5
  mid-session").
  - Combined: local 7B does the cheap turns; when it stalls, Odysseus's
  escalation logic issues one RPC command and the big model picks up with
  everything the small one already learned. Neither has this: Odysseus lacks the
  portable-context runtime, pi lacks the policy brain deciding when to
  escalate.

  3. One GPU, one model pool, every surface

  - pi consumes OpenAI-compatible endpoints but cannot create them — no hardware
  probing, no VRAM-fit scoring, no download/serve (that's Cookbook:
  services/hwfit/, src/cookbook_serve_lifecycle.py).
  - Odysseus serves models but has no terminal-grade agent runtime to spend them
  on.
  - Combined: Cookbook decides what fits your card and serves it once; chat,
  research, and the agent all draw from the same VRAM. Two standalone tools
  would each manage (or fail to manage) models separately.

  4. A policy boundary around an agent that has none

  - pi is single-user, fully trusted, no permission system (what-is-pi.md:63) —
  it can never safely be given to your family/team or to unattended automation.
  - Odysseus is multi-user with server-side scoped tokens
  (integrations/claude/README.md:32-36) and per-user privileges (core/auth.py) —
  but the agent inside that boundary is its weakest component.
  - Combined: each user gets a bounded pi — capability-stripped at spawn
  (--tools, usage.md:198), scope-checked at the API. pi gains an audience it
  could never have; Odysseus gains a runtime worth bounding.

  5. Scheduled, autonomous agents that reach your phone

  - pi has no scheduler, no notifications, no inbox to watch — someone must sit
  at the terminal.
  - Odysseus has cron tasks (src/task_scheduler.py), ntfy push, email triage,
  webhooks — but only its limited native loop to act on them.
  - Combined: "every morning at 7, read overnight email, cross-check my
  calendar, push a briefing to my phone" — Odysseus triggers and notifies, a pi
  one-shot (pi --mode json -p, docs/json.md) does the multi-step reasoning.
  Agentic automation, not agentic sessions.

  6. One agent session, every device

  - pi is terminal-only; its sessions are portable JSONL files
  (docs/session-format.md).
  - Odysseus is a responsive PWA (README.md:24) with SSE streaming and
  stop/resume.
  - Combined: start a task in the terminal at your desk, then steer the same
  session from your phone — Odysseus spawns pi with switch_session
  (rpc.md:564-580) on the same file and bridges steer to a mobile UI. Neither
  project has any path to this alone.

● Per the report's own filter — which gains strictly require the combination —
  the answer is Gain #1: a long-horizon agent that actually knows you.

  That's the one to anchor on, because:

  - Odysseus can't reach it alone — its native loop caps out (MAX_AGENT_ROUNDS =
  50, src/agent_tools.py:22, no compaction). It has the personal context but
  not the endurance.
  - pi can't reach it alone — it runs for hours (auto-compaction, session trees)
  but is amnesiac by design (what-is-pi.md:61-65). It has the endurance but
  knows nothing about you.
  - Only the pair clears the bar: tasks like "work through this 200-email
  backlog, update my todos and calendar, keep a running summary doc" need both
  durable personal context and a loop that survives 100+ turns. Neither could
  get there by just adding a feature at reasonable cost.

  The close runner-up is Gain #2: context-preserving model escalation — Odysseus
  already has the escalation policy (src/teacher_escalation.py) but throws away
  session state on restart; pi's mid-session set_model (rpc.md:217-233) keeps
  the full context. Combined, the local model hands off to the strong one with
  everything it already learned. It's #2 not #1 because it's an efficiency
  multiplier on the loop, whereas #1 is a capability that simply doesn't exist
  in either system.

  The other four gains (shared model pool, policy boundary, scheduled
  phone-reaching agents, cross-device sessions) are real but not strictly
  emergent — either project could in principle grow the missing half, just more
  expensively than integrating.

  So: #1 is the headline; #2 is the multiplier. Both trace to the same asymmetry
  — Odysseus's stateful periphery + pi's stateless, model-portable core — and
  both inherit the one open risk worth settling first: whether your local models
  drive pi's native tool-calling reliably (report's open question #4).
