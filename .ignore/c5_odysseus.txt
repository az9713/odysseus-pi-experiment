 Implementation Plan — Gain #1: a long-horizon agent that knows you (pi inside
 Odysseus)

 Context

 The report docs/odysseus-pi-integration-assessment.md identified Gain #1 as
 the single most meaningful outcome of combining Odysseus and pi: a personal
 agent that runs for many turns (pi's auto-compaction + session trees) and
 carries durable knowledge of the user (Odysseus's memory). Neither tool
 reaches this alone — Odysseus's native loop caps at 50 rounds with no
 compaction (src/agent_tools.py:22); pi is amnesiac by design
 (docs/what-is-pi.md:61-65).

 This plan embeds pi as a new Odysseus session backend (mode="pi") driven over
 JSONL-RPC, with a thin TypeScript "bridge" extension that (a) gives pi a
 manage_memory tool backed by Odysseus's scoped API and (b) injects relevant
 memories into pi's system prompt each turn. Per the user's decisions:
 admin-only, memory read+write only, and local-model support is mandatory — so
 the first phase is a hard go/no-go spike, because pi assumes provider-native
 tool-calling while small local models may not deliver it reliably.

 All seams below were verified first-hand in both repos.

 ---
 Phase 0 — GO/NO-GO spike: can local models drive pi's tool loop? (build
 nothing else until this passes)

 Why first: This is the one risk no code-reading can resolve. If small local
 GGUFs can't reliably emit pi-native tool calls and stay coherent across a
 compacted long session, Gain #1 cannot be delivered on local models as-is, and
 we must adopt the fallback (below) before writing the integration.

 Steps
 1. Install pi: npm i -g @earendil-works/pi-coding-agent (Node ≥ 22.19 —
 packages/coding-agent/package.json:97), bin pi. Or build from the local tree
 (npm install && npm run build in packages/coding-agent).
 2. Register the user's actual local model via ~/.pi/agent/models.json with
 api: "openai-completions" pointing at the Cookbook/Ollama endpoint
 (packages/coding-agent/docs/models.md:18-35).
 3. Capability test (pi's own tools): pi -p "read README.md and tell me its
 first heading" and a write task. Observe whether the local model emits valid
 tool calls at all.
 4. Long-horizon test (RPC): drive pi --mode rpc from the Python example
 (packages/coding-agent/docs/rpc.md:1316-1350) through a 30+ turn task that
 crosses the auto-compaction threshold; watch for derailment, malformed tool
 calls, and post-compaction coherence.

 Gate
 - PASS (local model reliably tool-calls + survives compaction) → proceed to
 Phase 1.
 - FAIL → adopt the fallback: route weak local models to Odysseus's existing
 native loop (src/agent_loop.py, built for them) and reserve pi for strong
 models (large local or API), selected by model capability. Gain #1 then
 applies where the model can sustain it, degrading gracefully. Re-scope Phase 1
 around this routing before building.

 ---
 Phase 1 — Memory bridge (the "knows you" half)

 1a. New memory-search endpoint (reuse existing retrieval)

 The current API only lists all memories (routes/codex_routes.py:267-272);
 Odysseus's ranked hybrid retrieval (vector + keyword + recency) lives in
 src/chat_processor.py:24-31 / src/memory_vector.py and is not exposed. Add:

 - POST /api/codex/memory/search (scope memory:read) in routes/codex_routes.py,
 body {query, k}, that calls the existing retrieval function (do not
 reimplement ranking) and returns scored memories. Add/write already exist
 (POST/DELETE /api/codex/memory, routes/codex_routes.py:274-354); no
 memory-update endpoint exists, so updates are delete + re-add.

 1b. In-code token mint helper

 Extract mint_api_token(owner, scopes, name) -> raw_token from the body of
 create_token (routes/api_token_routes.py:123-140) so it can be called outside
 a request. The route keeps calling it. Used to mint a per-session token scoped
 to memory:read,memory:write when a pi session starts; store encrypted (reuse
 EncryptedText, core/database.py:57-79) or in-memory keyed by session; revoke
 on session end.

 1c. The bridge extension (integrations/pi/extension/odysseus-bridge.ts)

 A single async extension (build to JS; pass via -e). It does three things:

 - Registers the provider from env Odysseus injects (ODYSSEUS_MODEL_BASE_URL,
 ODYSSEUS_MODEL_ID) via pi.registerProvider(..., { api: "openai-completions" })
 — pattern: examples/extensions/custom-provider-anthropic/index.ts:568-604,
 shape custom-provider.md:100-130. Avoids a global models.json.
 - Registers manage_memory tool (pi.registerTool, async execute doing fetch →
 /api/codex/memory* with Authorization: Bearer $ODYSSEUS_API_TOKEN) — actions
 search (→ 1a) and add (→ existing POST). Template:
 examples/extensions/dynamic-tools.ts:24-74.
 - Injects memories each turn via pi.on("before_agent_start", ...) returning
 {systemPrompt} — fetch relevant memories for event.prompt from
 /api/codex/memory/search and prepend. Template:
 examples/extensions/prompt-customizer.ts:86-96; result shape
 src/core/extensions/types.ts:631-641.

 ---
 Phase 2 — The RPC backend and session wiring (the "runs long" half)

 2a. Python RPC backend (src/pi_backend.py, new)

 An async generator (so agent_runs can drain it) that:
 1. Spawns pi with asyncio.create_subprocess_exec (NOT blocking Popen —
 blocking readline in an async generator would stall the event loop). Pipes
 stdin/stdout; apply detached_popen_kwargs() (core/platform_compat.py:46-61)
 for clean process-group kill.
   - Flags: --mode rpc --session-dir data/pi_sessions/<sid> --model <id>
 --system-prompt "<assistant persona>" --tools manage_memory -e <bridge.js>
 --no-skills. The --tools manage_memory allowlist excludes pi's built-in
 bash/read/write/edit — verified to filter built-ins (src/core/sdk.ts:244-250,
 agent-session.ts:2285). (Admin host tools can be added in a later phase.)
   - Env: ODYSSEUS_URL, ODYSSEUS_API_TOKEN (minted in 1b),
 ODYSSEUS_MODEL_BASE_URL, ODYSSEUS_MODEL_ID.
 2. Sends {"type":"prompt","message": <user msg>} (rpc.md:43-49).
 3. Reads pi's JSONL events and translates them to Odysseus SSE strings (data:
 {json}\n\n), yielding each. Mapping (pi → Odysseus, event names from
 rpc.md:741-985 and routes/chat_routes.py:691-1093):
 | pi event                    | Odysseus SSE
  |
 |-----------------------------|-----------------------------------------------
 --|
 | message_update / text_delta | delta {text}
  |
 | tool_execution_start        | tool_start {tool_name, tool_input}
  |
 | tool_execution_end          | tool_output {tool_name, tool_output, success}
  |
 | usage / get_session_stats   | metrics {input_tokens, output_tokens}
  |
 | agent_end                   | persist messages + message_saved + data:
 [DONE] |

 4. On cancel (GeneratorExit/aclose()): send {"type":"abort"}, then
 kill_process_tree(pid) (core/platform_compat.py:101-130). This binds process
 lifecycle to the run — no separate registry needed for v1.
 5. On agent_end: write user + assistant ChatMessage rows
 (core/database.py:161-188) so the session list/history UI works; pi's
 --session-dir JSONL remains the canonical transcript (mirror, don't mutate).

 2b. Dispatch wiring (routes/chat_routes.py)

 At the mode branch (chat_routes.py:494-497), add a "pi" path: build the
 pi_backend async generator, hand it to agent_runs.start(session, gen)
 (src/agent_runs.py:141), and return
 StreamingResponse(agent_runs.subscribe(session)). Stop/resume endpoints need
 no change — they already operate on agent_runs (chat_routes.py stop/resume;
 agent_runs.stop/subscribe).

 2c. Session creation (admin entry point)

 Session.mode already supports new values (core/database.py:129). Add a minimal
 admin-only way to create a mode="pi" session (a "New pi agent" action that
 POSTs /api/session then sets mode). Frontend rendering needs no change — the
 backend emits the same SSE event types the existing parser dispatches on
 (static/js/chat.js).

 Reused (do not rebuild)

 - src/agent_runs.py — detached run buffer/replay/stop; backend-agnostic, used
 as-is.
 - core/platform_compat.py — detached_popen_kwargs, kill_process_tree,

 - /api/codex/* memory add/delete + scope enforcement (_scope_owner,

 - Existing hybrid memory retrieval (src/chat_processor.py,

 - No memory update (delete + re-add).

 Implementation Plan — Gain #1: a long-horizon agent that knows you (pi inside
 Odysseus)

 Context

 The report docs/odysseus-pi-integration-assessment.md identified Gain #1 as
 the single most meaningful outcome of combining Odysseus and pi: a personal
 agent that runs for many turns (pi's auto-compaction + session trees) and
 carries durable knowledge of the user (Odysseus's memory). Neither tool
 reaches this alone — Odysseus's native loop caps at 50 rounds with no
 compaction (src/agent_tools.py:22); pi is amnesiac by design
 (docs/what-is-pi.md:61-65).

 This plan embeds pi as a new Odysseus session backend (mode="pi") driven over
 JSONL-RPC, with a thin TypeScript "bridge" extension that (a) gives pi a
 manage_memory tool backed by Odysseus's scoped API and (b) injects relevant
 memories into pi's system prompt each turn. Per the user's decisions:
 admin-only, memory read+write only, and local-model support is mandatory — so
 the first phase is a hard go/no-go spike, because pi assumes provider-native
 tool-calling while small local models may not deliver it reliably.

 All seams below were verified first-hand in both repos.

 ---
 Phase 0 — GO/NO-GO spike: can local models drive pi's tool loop? (build
 nothing else until this passes)

 Why first: This is the one risk no code-reading can resolve. If small local
 GGUFs can't reliably emit pi-native tool calls and stay coherent across a
 compacted long session, Gain #1 cannot be delivered on local models as-is, and
 we must adopt the fallback (below) before writing the integration.

 Steps
 1. Install pi: npm i -g @earendil-works/pi-coding-agent (Node ≥ 22.19 —
 packages/coding-agent/package.json:97), bin pi. Or build from the local tree
 (npm install && npm run build in packages/coding-agent).
 2. Register the user's actual local model via ~/.pi/agent/models.json with
 api: "openai-completions" pointing at the Cookbook/Ollama endpoint
 (packages/coding-agent/docs/models.md:18-35).
 3. Capability test (pi's own tools): pi -p "read README.md and tell me its
 first heading" and a write task. Observe whether the local model emits valid
 tool calls at all.
 4. Long-horizon test (RPC): drive pi --mode rpc from the Python example
 (packages/coding-agent/docs/rpc.md:1316-1350) through a 30+ turn task that
 crosses the auto-compaction threshold; watch for derailment, malformed tool
 calls, and post-compaction coherence.

 Gate
 - PASS (local model reliably tool-calls + survives compaction) → proceed to
 Phase 1.
 - FAIL → adopt the fallback: route weak local models to Odysseus's existing
 native loop (src/agent_loop.py, built for them) and reserve pi for strong
 models (large local or API), selected by model capability. Gain #1 then
 applies where the model can sustain it, degrading gracefully. Re-scope Phase 1
 around this routing before building.

 ---
 Phase 1 — Memory bridge (the "knows you" half)

 1a. New memory-search endpoint (reuse existing retrieval)

 The current API only lists all memories (routes/codex_routes.py:267-272);
 Odysseus's ranked hybrid retrieval (vector + keyword + recency) lives in
 src/chat_processor.py:24-31 / src/memory_vector.py and is not exposed. Add:

 - POST /api/codex/memory/search (scope memory:read) in routes/codex_routes.py,
 body {query, k}, that calls the existing retrieval function (do not
 reimplement ranking) and returns scored memories. Add/write already exist
 (POST/DELETE /api/codex/memory, routes/codex_routes.py:274-354); no
 memory-update endpoint exists, so updates are delete + re-add.

 1b. In-code token mint helper

 Extract mint_api_token(owner, scopes, name) -> raw_token from the body of
 create_token (routes/api_token_routes.py:123-140) so it can be called outside
 a request. The route keeps calling it. Used to mint a per-session token scoped
 to memory:read,memory:write when a pi session starts; store encrypted (reuse
 EncryptedText, core/database.py:57-79) or in-memory keyed by session; revoke
 on session end.

 1c. The bridge extension (integrations/pi/extension/odysseus-bridge.ts)

 A single async extension (build to JS; pass via -e). It does three things:

 - Registers the provider from env Odysseus injects (ODYSSEUS_MODEL_BASE_URL,
 ODYSSEUS_MODEL_ID) via pi.registerProvider(..., { api: "openai-completions" })
 — pattern: examples/extensions/custom-provider-anthropic/index.ts:568-604,
 shape custom-provider.md:100-130. Avoids a global models.json.
 - Registers manage_memory tool (pi.registerTool, async execute doing fetch →
 /api/codex/memory* with Authorization: Bearer $ODYSSEUS_API_TOKEN) — actions
 search (→ 1a) and add (→ existing POST). Template:
 examples/extensions/dynamic-tools.ts:24-74.
 - Injects memories each turn via pi.on("before_agent_start", ...) returning
 {systemPrompt} — fetch relevant memories for event.prompt from
 /api/codex/memory/search and prepend. Template:
 examples/extensions/prompt-customizer.ts:86-96; result shape
 src/core/extensions/types.ts:631-641.

 ---
 Phase 2 — The RPC backend and session wiring (the "runs long" half)

 2a. Python RPC backend (src/pi_backend.py, new)

 An async generator (so agent_runs can drain it) that:
 1. Spawns pi with asyncio.create_subprocess_exec (NOT blocking Popen —
 blocking readline in an async generator would stall the event loop). Pipes
 stdin/stdout; apply detached_popen_kwargs() (core/platform_compat.py:46-61)
 for clean process-group kill.
   - Flags: --mode rpc --session-dir data/pi_sessions/<sid> --model <id>
 --system-prompt "<assistant persona>" --tools manage_memory -e <bridge.js>
 --no-skills. The --tools manage_memory allowlist excludes pi's built-in
 bash/read/write/edit — verified to filter built-ins (src/core/sdk.ts:244-250,
 agent-session.ts:2285). (Admin host tools can be added in a later phase.)
   - Env: ODYSSEUS_URL, ODYSSEUS_API_TOKEN (minted in 1b),
 ODYSSEUS_MODEL_BASE_URL, ODYSSEUS_MODEL_ID.
 2. Sends {"type":"prompt","message": <user msg>} (rpc.md:43-49).
 3. Reads pi's JSONL events and translates them to Odysseus SSE strings (data:
 {json}\n\n), yielding each. Mapping (pi → Odysseus, event names from
 rpc.md:741-985 and routes/chat_routes.py:691-1093):
 | pi event                    | Odysseus SSE
  |
 |-----------------------------|-----------------------------------------------
 --|
 | message_update / text_delta | delta {text}
  |
 | tool_execution_start        | tool_start {tool_name, tool_input}
  |
 | tool_execution_end          | tool_output {tool_name, tool_output, success}
  |
 | usage / get_session_stats   | metrics {input_tokens, output_tokens}
  |
 | agent_end                   | persist messages + message_saved + data:
 [DONE] |

 4. On cancel (GeneratorExit/aclose()): send {"type":"abort"}, then
 kill_process_tree(pid) (core/platform_compat.py:101-130). This binds process
 lifecycle to the run — no separate registry needed for v1.
 5. On agent_end: write user + assistant ChatMessage rows
 (core/database.py:161-188) so the session list/history UI works; pi's
 --session-dir JSONL remains the canonical transcript (mirror, don't mutate).

 2b. Dispatch wiring (routes/chat_routes.py)

 At the mode branch (chat_routes.py:494-497), add a "pi" path: build the
 pi_backend async generator, hand it to agent_runs.start(session, gen)
 (src/agent_runs.py:141), and return
 StreamingResponse(agent_runs.subscribe(session)). Stop/resume endpoints need
 no change — they already operate on agent_runs (chat_routes.py stop/resume;
 agent_runs.stop/subscribe).

 2c. Session creation (admin entry point)

 Session.mode already supports new values (core/database.py:129). Add a minimal
 admin-only way to create a mode="pi" session (a "New pi agent" action that
 POSTs /api/session then sets mode). Frontend rendering needs no change — the
 backend emits the same SSE event types the existing parser dispatches on
 (static/js/chat.js).
